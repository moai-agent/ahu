# Release notes for 0.11.1

This patch prepares Rust-only ahu-maintained customer executables. Python remains
allowed for development tests, fixtures and tooling, but is not required to
install or run ahu or the maintained executable plugins.

## External plugin replacements

The coordinated plugin updates are GitHub CLI/tracker 0.1.1 and cmux host 0.2.1.
Both replace their Python implementations with standalone Rust executables.
Their provider operations and wire protocols remain unchanged. GitHub still
requires the native `gh` CLI and its authentication; cmux still requires a working
native cmux session. The GitHub plugins remain optional. The cmux host implements the standalone
session-host protocol for older host integrations; this core no longer creates
interactive task sessions through that protocol. Headless tasks and direct
coordinators do not require it.

Build the plugin for the target operating system and architecture before
computing its package digest. Source directories are no longer directly
installable executable packages. Follow each plugin's updated build and staging
instructions, then review the new version and content pins before updating the
project binding. Installation copies verified content; it never builds source.
Compatibility pins are exact: set `compatibility.ahu` to `"0.11.1"` when using
this CLI version, and retain `host_api: 1`. Before upgrading the CLI or changing
a host binding, finish and remove tasks using the old host with the old CLI and
binding still available. Their frozen host identity must remain usable for
cleanup. Then upgrade the CLI, review and commit the new package/version/content
and compatibility pins, and explicitly update the installed plugins. Companion
skills remain optional text guidance.

The independent text-stats plugin authoring example also uses Rust. Its tests
and the release OTel fixture now stage the compiled executable before install.

The obsolete Python Ollama server example has been removed. Use the existing
Rust-native Ollama decision provider with Ollama 0.35+ and a compatible decision
model; arbitrary chat models are not interchangeable with that API. The generic
decision HTTP contract remains available for independently maintained services.

## External harness runtimes

Codex, Claude Code, Antigravity, OpenCode, and Kiro now use separate Rust
harness-runtime packages. Core retains task ownership, process supervision,
permissions, MCP, and telemetry. Native launch construction, configuration
inspection, authentication probes, and event decoding belong to the installed
runtime. A missing or turned-off runtime has no built-in fallback.

Build and stage each runtime, review its content digest and exact core-version
compatibility, commit the binding and `harness-runtime` grant, then install it.
Discovery and setup preparation do not execute or implicitly enable packages.
The repository's workstation-specific development bindings are excluded from
Cargo release packages and Git source archives. Projects create their own
reviewed bindings.

Registered task execution is headless. Work mode explicitly requests native
automatic approvals and skips guarded native-configuration admission; it is
not a filesystem sandbox. Guarded launches retain configuration checks and may
refuse current native versions or unresolved account settings. A successful
work-mode test does not certify guarded mode. Direct coordinator sessions keep
their native interactive interface; the former interactive task/session-host
lifecycle is removed. Existing task records and frozen provider identity must
be preserved for inspection and cleanup during upgrades.

Work-mode child grants now retain the same uninspected native-configuration
inventory as their launch plans, allowing explicitly authorized registered
children to start. Guarded child grants still freeze and verify the inspected
inventory.

Release validation distinguishes successful task completion, actual MCP calls,
task-attributed telemetry, resume, cancellation, timeout, and cleanup. Native
model, token, cost, and helper observations can remain partial or unavailable.
See the [runtime contract](../harness-runtime-contract.md) and
[reference](../reference.md) for controls and evidence limits. Earlier pilot and
compatibility observations are historical evidence, not certification of this
candidate or every advertised native interface.

## Repository-local storage

ahu-owned operational data now belongs under the owning repository's ignored
`.ahu/`: task worktrees, private context acceptance, evaluation artifacts,
private numeric associations, plugin packages, and temporary executable
snapshots. Repository-wide data uses the primary checkout; task-local state
uses its task checkout. Native harness credentials and session history retain
their native locations. Raw captures and local results must not be committed or
published.

New task worktrees use `.ahu/worktrees/`. Legacy `.worktrees/` tasks remain
readable; upgrading does not move or delete them automatically. Review task
ownership and live processes before cleaning historical stores. Existing
external records and historical home stores require explicit migration; they
are not silently reassigned to the current repository. Explicit external
record destinations remain available when requested.

The guarded headless planner no longer asks a runtime for an interactive plan
before preparing the headless invocation. This allows runtimes that support
headless automatic approvals but refuse interactive automatic approvals to
reach the appropriate headless admission checks.

Headless capture errors discovered during the final stream drain now retain the
`capture_failed` outcome even when the native process has already exited. An
already recorded cancellation, timeout, or boundary violation keeps its original
outcome.
