# Release notes for 0.11.0

Version **0.11.0** supports optional session-host and tracker plugins around a
provider-neutral core, and improves agent coordination, structured child results,
MCP skill access, and unattended execution. These notes describe the
candidate behavior; publication and validation status are reported separately
with the release.

## Release scope

Keep core focused on harness launch, task/attempt state, Git worktrees, MCP
coordination and bounded telemetry/evaluation. Use skills with existing command-line tools
first; add an external executable plugin when a workflow needs a structured
integration. Provider API calls, authentication, issue transitions and terminal
workspace mappings belong to those integrations. Neither cmux nor GitHub is
required for current-terminal or headless execution.

The cmux session-host package and GitHub CLI/tracker packages are separate
repositories. Executable plugins run as local code with the user's access;
pins and grants control ahu invocation, not OS confinement. One-shot plugin
invocation is foreground/operator-only and task observations are read-only.
This release does not add automatic tracker synchronization or a generic
plugin task-mutation service. See [plugin architecture](../plugin-architecture.md).

## Agent coordination and structured results

Registered agents can declare bounded JSON contracts for child results. A
parent task can dispatch children, validate their completed output against the
declared contract, persist accepted results, and reconcile the child lifecycle.
Contracts reject reserved parser marker keys and enforce bounded parsing before
schema construction. Durable result reads apply the same protections. This
validates result shape and provenance; it does not make child output trusted or
replace review of actions taken by an agent.

Bundled ahu skills are available through the MCP skills/list and skills/get
methods. The guidance for typed decision requests now includes a valid minimal
request and explains why empty probes should not be sent; request validation
remains strict.

## Interactive host and Codex compatibility

The interactive session host boundary is separated from repository and launch
logic, making host lifecycle behavior easier to exercise independently. The
current terminal is the default interactive host, so ordinary builds need
no cmux installation. cmux is available through an explicitly selected,
committed executable Host V2 plugin; ahu no longer includes a compiled adapter. Headless execution also needs no session host.
Projects can also activate a package-backed Host V2 implementation through a
committed, enabled binding with the `interactive-backend` grant. Before launch,
ahu verifies package compatibility and the pinned source, then freezes the
binding, executable digest, and protocol in task schema 6. Focus, cancellation,
reconciliation, and removal use that frozen host identity; task records without a frozen external host identity fail closed. Package inventory remains side-effect-free, while
`ahu plugins --probe` explicitly activates the selected host. Installation
verifies and copies pinned content without executing it.

Projects that use OpenCode's native account/authentication state for headless
tasks can explicitly trust it in `.agents/ahu/config.md`. ahu records the
decision and warns that native state may activate remote configuration and
executable plugins; the default remains fail-closed.

Issue tracking remains an agent workflow: projects can provide skills for the
installed tracker CLI and their own policies. ahu core does not probe tracker
command-line tools, forward tracker credentials, or couple task lifecycle to issue state.
Projects that need a structured adapter can install an executable plugin; its
provider behavior and authentication remain outside the ahu host. This release
adds no GitKB behavior. See the
[host boundary](../reference.md#interactive-host-boundary) for activation and
trust limits.

Codex
headless configuration inspection now treats an empty declarative `notify`
setting as empty configuration, and Codex CLI version parsing is consistent
between compatibility admission and isolation profiles. Unsupported or
malformed settings continue to fail closed. These checks do not establish
compatibility with every live provider configuration.

## Shared project documents

New project settings and generated context locks use OKF 0.2 Markdown with
actual YAML frontmatter. Operational settings remain strictly typed; unknown
metadata and Markdown remain descriptive. Bounded legacy TOML readers preserve
existing task inspection and exact recorded inputs. Native harness files retain
their native formats, and credentials and local bindings remain private.

`ahu migrate --preview` shows deterministic targets and effective policy parity.
`--apply` explicitly converts legacy policy and locks, including mixed-format
projects, with exact backups and interruption recovery through `--rollback`.
Duplicate formats, stale context and changed HEAD refuse migration. An existing
canonical policy retains its exact bytes; canonical lock annotations survive
refresh. See [shared project documents](../project-documents.md) for the source
inventory, bounds, supported states and recovery procedure.

## Unattended tasks and evaluations

Explicit interactive auto tasks prepare native folder trust for their exact
verified Claude, Antigravity or Codex task worktree. Removal reverses trust added by
ahu while preserving existing trust and native history. Claude also approves
only the ahu project MCP server for that invocation. Worktrees remain ordinary
Git directories, not sandboxes; native managed policies can still deny work.

`ahu eval run --work-mode` selects the existing unattended work-mode path for
both candidates and optional agent evaluators. Guarded headless execution
remains the default. Reports distinguish these modes in their comparison
fingerprints, so results with different execution controls are not pooled.

Evaluations receive ahu OpenTelemetry through a temporary loopback receiver
and retain bounded results under the primary checkout's ignored `.ahu/evals/`.
Raw run artifacts and collector captures stay outside repositories. Missing
native token or trajectory observations remain unknown; complete ahu MCP
session telemetry does not mean complete native harness visibility. Provider
quota failures are recorded as unsuccessful attempts, not compatibility passes.

## Ownership and cleanup fixes

Default session-host selection now considers only bindings with an explicit
`interactive-backend` grant. Read-context and one-shot execution grants do not
select a terminal host. Interrupted host reads are retried rather than reported
as unsolicited protocol output.

The external cmux package binds task references to the exact workspace, window
and group plus repository/worktree scope. A replacement workspace at the same
path is not the same session. Lost creation replies with no recorded reference
remain uncertain; directory equality alone never authorizes cleanup. Older
local directory-only references are not accepted by the new package; existing
tasks retain their frozen package identity and must be reconciled before removal.

Task removal preserves Git-tracked configuration even when it was originally
materialized by ahu. Disposable copies are checked against the recorded launch
snapshot; modified task work is retained. Native trust cleanup restores only
ahu-added trust and preserves unrelated native state.

## Compatibility and upgrade limits

Shared policy and lock migration is explicit; it does not rewrite frozen task
records. The current task schema is 6. Older task schemas are refused rather than
silently interpreted or migrated. Review and integrate existing work before
retiring an older runner or its pinned host package.

Live evidence is specific to harness versions, models and execution modes.
The release focus is Claude Code, Codex and Antigravity interactive/headless
work, with OpenCode headless validation. OpenCode interactive support and Kiro
quota-blocked validation remain deferred. Missing provider credits are not a
compatibility pass, and available adapters do not certify every native setup.

## Validation boundaries

Fixture tests cover structured child-result validation through parent
reconciliation, MCP skill methods, Codex configuration admission, and typed
decision guidance. They do not prove live provider behavior. The release
candidate also requires the repository's full test, coverage, security,
documentation, and package-boundary checks before publication.
